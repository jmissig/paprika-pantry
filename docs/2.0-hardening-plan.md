# 2.0 hardening and dependency migration plan

Date: 2026-11-08
Status: planned; implementation not started.
Baseline: `c57227b` (2.0.0 Paprika 3/4 compatibility).

## Goal and boundaries

Finish the review findings before shipping 2.0.0: preserve canonical reads when
the disposable sidecar is unavailable, close publication races, make diagnostics
consistent, upgrade dependencies, and simplify concurrency and store ownership.

Required targets:

- Swift tools **6.2 minimum**, Swift 6 language mode, macOS 13 deployment minimum.
- GRDB **7.12.0**, allowing subsequent compatible 7.x releases via SwiftPM.
- ArgumentParser **1.8.2**, allowing subsequent compatible 1.x releases.
- Commit the resolved dependency versions when implementation is committed.

Keep Paprika read-only, the SQLite/GRDB stack, the rebuildable single-source
sidecar, explicit transition rebuilds, and independently refreshed pairing evidence.
Keep Collections as our term for Paprika's Cookbooks; publication/source rollups
remain distinct. Do not add an ORM, daemon, database mirror, or new recipe features.

This plan does not authorize installation, toolchain replacement, app launch/sync,
tagging, pushing, or changing ambient sidecars. Keep private samples and benchmarks
in ignored local storage. Keep the CLI version at 2.0.0 for this pre-release pass.

## Evidence from review

- Reproduced on synthetic data: a readable Paprika source plus a future-version
  sidecar makes both plain `recipes list` and `recipes show` fail. Source status
  succeeds. Optional enrichment currently opens/migrates the sidecar unconditionally.
- Static finding: partial updates check compatibility separately from capturing
  baseline provenance; full rebuilds omit the final generation comparison.
- Static finding: index diagnostics obtain provenance, compatibility, counts and
  run information in separate reads, which can describe different generations.
- `BlockingAsync` bridges tasks with a semaphore and an unchecked result box.
  Source-bound queries use an optional contract and a boolean factory parameter.
  `PantryStore.swift` mixes reports/models, queries, orchestration and derivation.
- Baseline verification reported 106 passing tests and isolated v4 smoke checks.
  Those results do not establish compatibility with the proposed dependencies.

## 1. Correctness regressions and source/sidecar isolation

Primary files: `CLI/RecipeCommands.swift`, `CLI/CommandContext.swift`,
`Store/PantryDatabase.swift`, `Store/IndexCompatibility.swift`, CLI integration tests.

1. Add command-level regressions for missing, legacy, incompatible, future-version,
   corrupt and inaccessible sidecars, using explicitly configured synthetic sources.
2. Canonical list/detail commands must succeed without optional enrichment. Do not
   create or migrate a sidecar merely to attempt enrichment. Open existing evidence
   through a non-mutating inspection/read path, with a clear unavailable reason.
3. Report omitted enrichment honestly: no fabricated usage values or freshness
   timestamps. Preserve valid canonical results and distinguish source failures
   from sidecar failures. Do not broadly swallow errors around the whole command.
4. Commands with requested indexed filters/sorts, and inherently indexed commands,
   must fail clearly if their required evidence is unavailable. Never silently drop
   a filter. Give `index rebuild` guidance when rebuild is the remedy; future-version
   stores require a compatible binary or a separately selected sidecar, not mutation.
5. Make diagnostics resilient: `doctor` should still describe source health when
   the sidecar cannot be opened. Keep schema migration in explicit index-writing
   operations; do not mutate future-version stores during any read/diagnostic path.
6. Reuse one selected source instance/contract per command rather than reopening
   independently for canonical reads and enrichment binding.

Acceptance: canonical rows remain available in every sidecar failure fixture;
indexed requests fail with the expected reason; read-only operations do not create,
migrate or alter the fixture sidecar. Verify text and JSON behavior.

## 2. Coherent build baseline and guarded publication

Primary files: `Store/PantryStore.swift`, `Store/IndexCompatibility.swift`,
`Tests/PantryKitTests/PaprikaSQLiteSourceTests.swift` and store tests.

Use optimistic generation validation, not a database write lock held throughout
expensive extraction and derivation:

1. Capture the sidecar baseline before taking the source snapshot. Capture all
   relevant family contracts, generations and dependency signatures in one read
   transaction. Validate partial-update compatibility against that same captured
   baseline once the snapshot's source contract is known.
2. Build incremental skip decisions from a coherent baseline. Couple existing
   indexed-row reads to a generation check in their read transaction so they cannot
   silently come from a different publication than the captured baseline.
3. At publication, compare the current baseline token inside the write transaction
   for **both** full rebuilds and partial updates. Reject any intervening publication
   before deleting or inserting final rows. Do not automatically retry expensive work.
4. A full rebuild may intentionally change source/layout, but must not overwrite a
   writer that published after its baseline capture. A partial update must not retain
   rows from a different source and stamp them with its own source contract.
5. Keep final rows, successful run state and per-family provenance atomic. Preserve
   old results on failure. Capture run creation/attempt metadata coherently and
   include setup failures in cleanup handling, not only extraction/write failures.
6. Read index statistics, compatibility, provenance and relevant run metadata in
   one SQLite read transaction. Keep query validation and evidence reads atomic too.

Deterministic regression coverage (barriers/hooks, not timing sleeps):

- Competing publication between baseline capture and source snapshot/extraction.
- Competing source/contract change at the former compatibility/provenance gap.
- Full rebuild racing a full rebuild and racing a partial update.
- Older work finishing after newer work cannot replace the newer generation.
- Rejected publication leaves committed rows/provenance intact and records failure.
- Diagnostics cannot combine counts/readiness from one generation with another's
  provenance. Routine updates preserve pairing provenance.

## 3. Swift tools 6.2 and dependency migration

Treat this as its own implementation slice after the correctness tests exist.

1. Record `swift --version` and the active toolchain. The review host has Swift
   6.2.4, sufficient for the requested tools minimum; no installation is needed.
2. Set `// swift-tools-version: 6.2`. Retain Swift 6 language mode and macOS 13.
   Do not opt into default MainActor isolation or unrelated upcoming features.
3. Follow GRDB's preparatory guidance: check the latest 6.x maintenance release and
   resolve applicable deprecation warnings before switching to 7.x. Do not publish
   an intermediate release merely for this preparation.
4. Set dependency lower bounds to GRDB 7.12.0 and ArgumentParser 1.8.2; resolve and
   review `Package.resolved`. Use the tagged releases, not upstream branch heads.
5. Inventory GRDB call sites: synchronous/asynchronous reads and writes, backup,
   migrations, schema introspection, row decoding, FTS and transaction boundaries.
   Address Sendable/compiler diagnostics deliberately rather than adding blanket
   `@unchecked Sendable` or `@preconcurrency` exemptions.
6. Verify GRDB 7's transaction semantics (DEFERRED reads, IMMEDIATE writes), and its
   cancellation behavior: cancelled async accesses can throw and roll back. Preserve
   attempt reporting without permitting cancelled work to publish final results.
7. Check removed APIs and direct SQLite imports if present. Re-audit remaining
   unchecked conformances after compiling against GRDB 7's concurrency annotations.
8. Test a sidecar produced with the old dependency under the new dependency. A GRDB
   library upgrade alone must not invalidate derived data or rewrite historical
   migration definitions. Change adapter/derivation contracts only if meaning changes.
9. Check ArgumentParser command resolution, global options, aliases, nested help,
   validation failures and text/JSON/CSV formats. Avoid its reverted 1.8.0 parsing
   behavior; target 1.8.2 explicitly.

Acceptance: debug build, full tests, release build and isolated CLI smoke checks
pass on the installed 6.2.x compiler. This verifies 6.2.x, not every Swift 6.2 patch
or an unavailable Swift 6.4 toolchain. A later 6.4 check is optional, not a new floor.

## 4. Native async CLI and explicit store roles

1. Convert the executable entry point and async command hierarchy to
   `AsyncParsableCommand`, using ArgumentParser's supported async entry path.
   Keep synchronous leaf work synchronous where useful; remove `BlockingAsync`
   once all consumers are migrated. Do not block an executor with a semaphore.
2. Keep option propagation explicit. Remove dependence on mutable process-global
   runtime options where the async command conversion would otherwise retain shared
   unsafe state; use command-owned options/context without inventing a DI framework.
3. Define cancellation checkpoints before expensive phases and before publication.
   Cancellation before commit must preserve the previous generation; cancellation
   after commit must not misreport a committed generation as rolled back. Verify
   failure/cancellation bookkeeping under GRDB 7. Do not promise graceful SIGINT
   handling unless separately implemented and demonstrated at process level.
4. Replace `bindToSource: Bool` and the optional production query contract with
   explicit factories/roles: source-bound evidence reader, index writer, and
   diagnostic inspector. A production evidence reader must require a contract.
   Keep unbound fixture support explicit and unavailable by accidental default.
5. Keep Paprika-specific snapshot/schema work behind the source boundary. Use a
   narrow build-input abstraction if necessary to remove concrete-source casts from
   orchestration; do not grow a generic multi-provider database framework.

Acceptance: no semaphore bridge remains; successful/error CLI behavior is preserved;
async cancellation and rollback tests pass; no production derived-query path can
accidentally omit compatibility validation. No new concurrency exemptions without
a documented ownership justification.

## 5. Mechanical store decomposition

Do this after behavior and dependency changes stabilize, in a separate diff.

- Keep the database schema/migrator in `PantryDatabase.swift`.
- Keep source contracts, generations and compatibility policy together.
- Extract read/query operations, build orchestration/publication, and pure
  time/ingredient/usage/pairing derivation into focused files/types.
- Move report/domain models out of the orchestration file where appropriate.
- Preserve one transaction owner for publication and one compatibility boundary
  for reads. Do not split transactions just to make files smaller.
- Preserve CLI output, SQL meaning, ordering and numerical results. Avoid a broad
  access-control expansion solely to make a mechanical file split compile.

Acceptance: unchanged fixtures produce equivalent results, with existing tests
passing. No new database engine, service layer hierarchy or package dependency.

## 6. Final validation, documentation and release boundary

- Run `make build`, `make test`, and `make release` for the final integrated state.
  Run focused tests during each slice; do not repeat expensive suites without a
  changed input or unresolved concern.
- On isolated v3/v4 sources and separate explicit homes: source status, doctor,
  canonical list/show, Collections, meals/groceries/pantry, rebuild then update,
  search/ingredients/usage/source rollups/pairings, and representative CSV/JSON.
- Cover legacy/future sidecars, source swaps, unchanged hashes, category changes,
  failed/cancelled publication, both concurrent-writer modes and no-sidecar reads.
- Compare source database/WAL hashes before and after isolated smoke testing.
  Keep timing/RSS comparisons local; investigate regressions without introducing
  incremental pairing work unless measurements justify that separate feature.
- README: Swift 6.2+ build prerequisite and any changed human recovery steps only.
  `docs/`, AGENTS.md and the repository skill: roles, cancellation, publication and
  diagnostic contracts. Mark superseded behavior in the prior compatibility docs.
- Remove the active TODO link when complete; preserve implementation evidence in
  tests and Git. Keep v4 app/preference discovery, null collection semantics and
  numeric time/nutrition adoption explicitly separate unresolved checkpoints.
- Report exact tests/toolchain/dependency versions and any gaps. Commit, install,
  tag and push only when requested; keep the existing commit history intact.

Suggested commit-sized slices: direct-read isolation; publication/diagnostic
correctness; Swift/dependency migration; async and explicit roles; mechanical
decomposition plus reconciled documentation. Each slice should remain buildable.
